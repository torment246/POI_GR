# GHR-SID：地理优先的层次关系碰撞标识

更新时间：2026-08-15。

当前状态：`EXP-20260814-09`“每个 POI 独立最短描述”和 `EXP-20260814-14`“桶共享强关系树”均已完成 4×RTX PRO 6000D 三轮 SFT、与 TIGER 相同的固定 10,000 条 Validation 无约束 Beam=10 评测，以及 epoch 3 全库合法路径约束诊断。EXP-14 epoch 3 无约束 HR@1/HR@10/NDCG@10 为 49.10%/79.70%/65.2636%，分别比 EXP-09 低 1.32/2.91/1.9770 个百分点；约束后进一步降至 45.92%/71.35%/59.3719%。桶共享关系树没有抵消目标变长和闭合带来的生成损失，当前不作为提升候选。两套目标都只由 POI 静态信息定义；Query、请求 GID 和历史仅作为 SFT 输入，不定义、不选择也不改变 SID。

## 1. 方法目标

GHR-SID（Geo-Hierarchical Relational Semantic ID）只替换 TIGER 三层基础 SID 后的无语义桶内碰撞编号。它不改变 TIGER/BGE-M3/RQ-VAE `1024×3` 主 SID，只在基础 SID 发生碰撞时增加由 POI 静态地理位置和数字关系决定的变长后缀。

北京第一版的结构为：

```text
TIGER S1/S2/S3
    → 最短粗粒度 Geohash 分支
    → 同一粗地理叶子内最多 3 个静态数字关系对
    → 关系仍同码时的最短细粒度 Geohash 分支
```

用户确认的当前版本把 `G6` 作为唯一地理层：`G6` 已经无法区分的 POI，后续只沿实体关系继续展开，不再加入 `G8/G9`，也不保留独立的粗 R3 阶段。EXP-09 基线形式为：

```text
TIGER S1/S2/S3 → 最短 G6 粗地理 → 最短可区分实体关系 → EOS
```

形式化为：

$$
\operatorname{SID}_{09}(p)=
\operatorname{TIGER}(p)
\oplus G_6(p)
\oplus D_{\min}(p).
$$

当前关系树版为：

```text
TIGER S1/S2/S3 → 最短 G6 粗地理 → 桶共享强关系树 → 可选局部 D → EOS
```

$$
\operatorname{SID}_{tree}(p)=
\operatorname{TIGER}(p)
\oplus G_6(p)
\oplus R_{tree}(p)
\oplus D_{leaf}(p).
$$

方法要解决的不是“让 Query 更容易预测某个局部序号”，而是把碰撞后缀改造成可复建、可解释的 POI 实体属性。最终是否提升仍只由同协议 SFT 检索指标判断，静态唯一率不单独算作下游提升。

## 2. 北京单城边界

当前数据目录只包含北京市 2,337,178 个在线 POI，因此首轮不输出城市 Token。北京城市根在方法中隐式固定；扩展多城市时，必须在地理路径之前增加外部提供的固定 `city_id`，不能从 Query 猜城市，也不能让同一 POI 随请求城市改变标识。

首轮构码只消费：

- 冻结 TIGER 三层基础 SID 与碰撞桶；
- POI `lng/lat` 生成的标准 Geohash；
- POI `displayname/address` 确定性抽取的严格数字关系；alias 只供人工审计，不参与当前关系树构码；
- POI 等权的静态桶内信息增益。

明确不消费：

- Query 文本或 Query embedding；
- Query–POI 点击/发单次数；
- 请求 GID；
- Train/Validation/Test 订单；
- 热度权重或按请求动态变化的 SID。

SFT 阶段仍然执行任务定义中的 `Query + 请求位置 → 固定 POI SID`，但 Query 和请求位置不参与定义目标 SID。

## 3. 为什么是地理优先

地图碰撞首先包含不同位置的同名连锁店。它们可能没有期数、楼栋、单元等关系差异，唯一稳定差异就是地理位置，因此先回答“在哪里”。同一园区、建筑或网格内的多个 POI 常共享坐标或坐标精度不足，此时再使用期数、楼栋、单元、楼层、房间、入口和门牌等关系回答“区域内部是哪一个”。

不能把地理无限细分后再声称关系无用。第一版预先固定一个业务粗层和一个细地理上限：

- 主协议：`Geohash6 → Relation(max=3) → Geohash8`；
- 结构敏感性：同次只报告 `G5→R3→G8` 和 `G7→R3→G8`；
- G5/G7 不用于看完结果后替换主协议，也不据此宣称模型选择收益。

Geohash6 在北京纬度约为公里级网格，适合先分开跨片区同名门店，并与现有请求 GID6 保持层级一致；Geohash8 只作为关系失败后的几十米级上限。若 POI 在 GID8、关系和值上仍完全相同，本轮诚实保留为不可语义区分残留，不追加 `poi_id` 排序伪装成语义码。

## 4. 最短层次路径

对一个 TIGER 碰撞桶，先省略该桶所有 POI 共享的 Geohash 前缀，从第一个地理差异位开始逐层分支。一个 POI 在某层成为单例后立即停止，不继续生成后续地理字符。

未由粗地理解决的叶子使用现有 17 类严格数字关系，以 POI 等权静态信息增益选择关系。关系缺失分支不消耗关系对预算；如果某个缺失分支只剩一个 POI，可以在当前节点直接 EOS，仍然是合法的变长唯一标识。

首轮中，关系后仍同码的叶子从共同细地理前缀之后继续展开，最多到 Geohash8。首轮顺序固定为：

```text
coarse GEO chars → relation type/value pairs → fine GEO chars
```

EXP-04 起按用户确认冻结为仅关系协议，当前通过门槛的 EXP-07 顺序为：

```text
coarse G6 chars → coarse relation pairs(max=3)
                → minimal fine entity relation pairs → EOS
```

`G6` 后不再出现 G8/G9；细关系候选数量不等于目标长度，EXP-07 虽有 67 类候选，实际路径最多 3 对。

EXP-09 进一步删除独立粗 R3，把原粗关系和细关系合并为统一的简洁角色本体，当前主协议为：

```text
coarse G6 chars → exact minimum distinguishing entity description(max=3 pairs/6 tokens) → EOS
```

统一本体共 80 类候选，其中 32 类是期区、楼栋、门牌、单元、楼层、房间、入口、道路、父子实体、类别和 layer 等角色，48 类是父子实体前后各 12 位的位置字符兜底。候选数不等于路径长度；完整角色实体为第一优先级，类别/layer 为第二优先级，位置字符只在前两级不能区分时启用。

地理字符和关系类型最终都映射到互不重叠的纯数字专用 Token 空间；POI target 中不写“号楼”“单元”“层”等中文。具体 Token ID、段标记和初始化方案在结构实验通过后再冻结，本轮不提前扩词表。

EXP-14 将主候选改成桶共享关系树。它只保留 21 个强角色；某个角色在桶内发生差异时激活该角色，同时补齐该 POI 已存在的上级关系。例如楼栋发生分叉时，共同的“4区”仍保留，形成 `4区→20号楼`，不会再压缩成单独 `20`。缺失关系直接跳过，不写伪造的 missing Token；语义路径完全相同的叶子才追加 `D`。这保证同一桶的所有路径都属于一棵按固定角色次序构造的合法 Trie。

## 5. 首轮结构指标与门禁

首轮只做 POI 等权的全量静态结构实验，分别报告：

1. 粗地理直接解决的碰撞 POI；
2. 同一粗地理叶子中由关系新增解决的 POI；
3. 关系后由细地理新增解决的 POI；
4. GID8 与关系仍相同的残留 POI/组及最大组；
5. 碰撞 excess 的消除比例；
6. 完整目录的静态 distinct identifier ratio；
7. 粗/细地理字符数、关系对数和序列化 Token 长度分布。

进入最终数值序列化实现至少要求：

- G6 主协议消除不少于 95% 的原始 collision excess；
- 平均新增语义原子不超过 3；
- 所有输出能够复现冻结 GID6 前缀、输入行数和碰撞行序；
- 构码 manifest 明确证明没有消费任何 Query 或订单数组。

满足这些条件只允许进入 mapping/Tokenizer/Trie 的下一最小步，不自动批准正式 SFT。最终 SFT 是否值得运行，还需结合残留碰撞、序列长度、Token 支持度和固定 10k 目标覆盖审计。

## 7. EXP-09 历史方法定义与问题边界

`绿茵花园别墅西区-春风区C12B号楼` 的 EXP-07 路径暴露了信息增益贪心的目标错位：它能用父实体字符“西”、类别和子实体首字符“春”把当前行分开，却没有保存真正决定楼栋身份的完整编号 `C12B`。这条路径在静态唯一性上成立，在实体逻辑、目标长度和生成难度上都不是合理最优解。

EXP-09 实现把两个问题严格分开：

1. **实体关系抽取**只由 POI 自身的稳定名称、地址、别名和分类产生，负责识别完整的门牌、楼栋、单元、楼层、房间、商铺、车位、入口、区域名和字母数字编号；
2. **关系路径选择**只比较同一个 post-G6 碰撞桶内的 POI，负责寻找能区别同桶其他实体的最短关系组合。

Query 不参与上述任一阶段。Query 是否包含实体、表达质量高低和点击频次都不能改变 POI 的关系定义；Query 只在最终固定 SID 后的 SFT 与检索评测中出现。

关系 schema 已升为 `ghr-sid-fine-entity-relations-v3`，新增角色化的 `R_FINE_BUILDING_CODE/R_FINE_ENTITY_CODE`。`E-058`、`12A`、`C11`、`C12B` 等编号会先规范化，再编码成一个全局可逆整数；若完整编号存在，旧的字母前缀、编号数字和同一编号内部的泛化子数字候选不再同时发射，避免优化器只取 `C`、`12` 或 `B`。该逻辑已通过合成测试，并由 EXP-09 北京全量实验验证。

EXP-09 不再使用桶级信息增益树作为主优化器，而采用“最短可区分描述”。对桶内 POI $p_i$ 的候选关系 $r$，定义它能排除的同桶实体集合：

$$
D_i(r)=\{p_j\mid p_j\neq p_i,\ v_j(r)\neq v_i(r)\}.
$$

寻找关系集合 $S_i$ 覆盖全部同桶其他实体，同时最小化真实数值 Token 长度：

$$
S_i^*=\arg\min_{S_i}\sum_{r\in S_i}c(r,v_i(r)),
\quad
\bigcup_{r\in S_i}D_i(r)=B\setminus\{p_i\}.
$$

其中 $c$ 按最终 base-1024 序列化后的实际 Token 数计算，而不是只数关系对。选择时使用硬语义层级：完整角色化实体关系优先，类别/layer 次之，位置字符只兜底；已识别实体内部的局部字符不允许击败完整实体。编译器通过候选去重、支配剪枝和深度不超过 3 的精确组合搜索完成，不需要训练模型。

EXP-10/11 后为关系树实验冻结的边界是：不再追加 G7+ 细地理，不再新增道路、邻近实体、相对方向、alias 或细地址关系。保留 EXP-09 已证明高收益的楼栋、单元、区域等主体关系，在最终仍碰撞的叶节点追加一个稳定的局部 Dedup Token；Dedup 只保证目录唯一，不被解释为语义提升。作为历史长度下界，EXP-09 只需对 59,601 个残留 POI 追加 Dedup，占全目录 2.5501%；继续补关系的可信名称+地址上限只有 1,681 excess，占原始 661,969 excess 的 0.2539 个百分点。EXP-14 为了获得桶内一致树形，实际将 Dedup 覆盖扩大到 165,299 个 POI；最终是否超过 TIGER 仍只看同协议 SFT 检索指标。

## 8. EXP-14 当前关系树定义与完整案例

### 8.1 数值 SID 约定

案例中的可读表示为：

```text
T(s1,s2,s3) / G(g...) / Rtype_id(value) ... / optional D(code) / EOS
```

- `T` 是冻结 TIGER 三层数字；
- `G` 只保存该 TIGER 桶公共地理前缀之后实际需要生成的 G6 分支，不重复生成桶内公共前缀；案例同时记录完整 GID6 字符与数字码；
- `Rtype_id(value)` 是纯数字“关系类型 + 关系值”。普通数字楼栋在统一命名空间中编码为 `2×楼栋号`，所以 `R6(40)` 解码为 `R_BUILDING=20`；`C12B` 等字母数字楼牌使用可逆 packed integer；
- `D` 只出现在语义叶子仍有多个原始 POI 时，按 POI ID 数值升序从 0 连续编号；
- `R_*` 名称只用于文档解释，模型 target 不混入“区、号楼、单元”等中文。

- GHR 主指标定义：给定正确 `[S1,S2,S3]`，并对每个后续位置使用 gold 前序后缀，要求目标中的所有 GHR 后缀 Token 和 `target_close` 在各自位置均为 Top-1，任一位置错误则该请求计错；
- 对照定义：TIGER 只有一个 `C` Token，既有 `C>0 条件 C Top-1` 是给定正确 `[S1,S2,S3]` 后该单 Token 的 Top-1。两者样本完全一致，但 GHR 需要同时正确多 Token 和闭合符，序列难度更严格；
- 假设：若 GHR 整段后缀在该严格同样本口径下已接近 TIGER，而端到端 HR 仍明显更低，则主要问题不应继续归因于局部碰撞后缀不可学习，而应转向自由生成中的三级 Bucket 覆盖和前序错误传播。

#### 结果

所有指标均为百分比；差值只用于同样本诊断。TIGER 是单 `C` Token，GHR 是“所有后缀 Token + `target_close`”整段同时正确。

| 方法 | 目标决策 | 样本数 | 条件 Top-1 all | 相对 TIGER |
|---|---|---:|---:|---:|
| TIGER | 单个 `C` Token | 2,356 | 81.0272 | — |
| GHR EXP-09 | 整段变长后缀 + 闭合 | 2,356 | **82.2581** | +1.2309pp |
| GHR EXP-14 | 整段变长后缀 + 闭合 | 2,356 | **81.6638** | +0.6366pp |
| GHR 固定 `32×32` | `R1/R2` + 闭合 | 2,356 | 80.3480 | -0.6792pp |

- EXP-09/14 即使要求整段后缀与闭合同时正确，gold-prefix 条件 Top-1 仍分别略高于 TIGER 单 `C`；固定 `32×32` 只低 0.6792pp。局部后缀可学习性不足无法解释三者端到端无约束 HR@10 相对 TIGER分别低 4.61/7.38/2.22pp；
- EXP-14 在 gold 前序后缀条件下表现良好，但自由生成中 Bucket→完整 HR@10 损失仍为 4.92pp，说明 Teacher-Forcing 隐藏了长变序列的前序错误传播、整序列分数竞争和提前闭合问题；
- 固定 `32×32` 的同样本后缀只比 TIGER 低 0.68pp，且此前 Bucket→完整损失已与 TIGER接近，因此其首要瓶颈仍是三级 Bucket HR@10 比 TIGER 低 2.09pp，而不是继续扩展碰撞后缀表达能力；
- 本实验不能据 82.26% 宣称 EXP-09 的实际自由后缀生成优于 TIGER：GHR 的每个位置都喂入 gold 前序 Token，端到端解码不会拥有该条件。
